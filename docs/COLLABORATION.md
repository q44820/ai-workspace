# 多AI协作工作流程

## 版本与事实来源

- main：已合并的协作代码版本，不自动等于生产版本。
- 每个项目STATUS：最后一次实际验证、未解决问题和下一步；发现陈旧记录先标待核验。
- 运行环境：另行核验；禁止从Git记录猜服务在线、余额或成交。

## 一个任务一个负责人

1. 先fetch并读取最新main；使用独立clone/worktree，避免多个AI共享同一工作树。
2. 按templates/task.md在tasks/建立唯一编号记录，写负责人、项目、范围和交接锁。
3. 分支命名 `task/<编号>-<简述>`；如同模块已有任务先协调，不覆盖别人改动。
4. 最小修改，先补复现/回归测试。外部服务和资金操作不因仓库可写而获得授权。
5. 更新项目STATUS、任务记录和CHANGELOG，写真实测试结果、限制、回退方式。
6. 运行 `python3 scripts/verify_workspace.py`、`python3 scripts/check_publication.py --all`，人工审查diff。
7. 创建PR并参考模板，附验证证据。需要部署时单独提案，禁止把合并自动当部署授权。
8. 合并后由实际有权限的负责人交接，不在旧摘要里延续已经撤销的授权。

## CI

仓库自带GitHub Actions，执行离线测试和提交内容检查。工作流不读取密钥，不部署，不发消息、不访问交易账户。代码或workflow变化需人工审查；CI绿灯不是策略收益证明。当前没有强制分支保护，也不能阻止owner直接推送。

## 更新优先级

P1：价差网页、LP监控。P2：机票。P3最低：Polymarket扫描、天气与跨平台预测市场。无新用户要求不自动安排低优先级常驻任务。

## 验收层级

- 语法通过：只能证明可解析。
- 离线测试：只能证明指定测试输入下行为正确。
- 实时只读验收：必须记录时间、数据来源和结果。
- 生产验收：必须另核验目标服务与用户侧效果，不能从前三项自动推出。
