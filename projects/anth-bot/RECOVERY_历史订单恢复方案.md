# 受污染状态的可审计恢复方案

本文件只是人工步骤。不要在服务器上执行，不要杀进程，不要清空 `state.json`，不要删除旧 intent，不要把 `filled` 写成一个没有官方成交支持的数字，不要把模式改回 live，也不要改 3x / 290U / 40bp。

## 已核对的事实

用户提供的脱敏证据：2026-11-21 03:34:15（上海）备份里同一批 16 条 intent 全部是 `terminal`。03:34:57 用当时已部署的程序重启，03:36:13 `venuesReady`，03:37:08 出现开仓信号。这个窗口没有新的 intent、cloid 或 `[order]` 日志。本地却出现 `opening_pending`、`entryAccountingUnknown`，以及 `exit_pending.submitted=true`、原因是开仓。

对照备份，同一批旧单被当前持仓复核改写：

- `#2` / `#3`（2026-11-17 Lighter，official id `113917744074459` 与 `204835031781534`）从 `terminal` 变成 `unknown`，终态证据被清空。
- `#13` / `#14`（2026-11-20 开仓，official id `0xd3f20e389bb4ce210e72c85907601ece` 与 `13096582632427`）从 `terminal` 变成 `terminal_wait`，`filled` 0.126 和官方订单证据还在。
- 随后的平仓 `#15` / `#16` 仍是 `terminal`，`filled` 0.126。

代码在发单前写 intent 和 `[order]` 日志。这两样都没有，所以这次开仓没有走到发单。两所当时仓位和挂单为 0。Hyperliquid 官方在该窗口的订单和 fills 为 0。Lighter 最近 50 笔公开成交窗口为 0，但其私有历史接口未签名返回 400。公开窗口为空不能证明绝对没有发单。

这不是一笔新的已提交未知订单。它是旧的已结算订单被按当前净持仓重新判定，污染了新会话。真正缺官方终态的新订单仍然要停在未知，不能用这份方案去填成交。

## 原因

`reconcile_orders` 用「当前净持仓是否等于该笔下单前持仓加本笔成交」决定旧单是不是做完。后面还有同所的开平时，这个等式对更早的单不再成立。查询窗口里找不到的旧 Lighter 单会被降成 `unknown` 并擦掉证据。发单前的未知门禁接着把这次还没发出的开仓写成已提交退出。

## 人工恢复顺序

1. 再复制一份当前 `state.json`。不要覆盖 03:34:15 备份。
2. 先部署并重启之外，不要靠再跑一遍旧程序“自己修好”。旧程序会继续按当前持仓改写。
3. `#13` / `#14`：证据仍是官方订单、`filled` 仍是 0.126，且同所已有更晚的平仓终态。新对账会把它们从 `terminal_wait` 调回 `terminal`，不改数量。这是恢复被错误降级的官方终态，不是新造一笔成交。
4. `#2` / `#3`：证据已经被擦掉，不能靠本地记忆把 0.174 写回去。只有 `audit_restore_intent` 可以恢复一条：当前记录和备份的 `official_id`、venue 一致，备份状态是 `terminal`，并且人工给出的官方成交数量与备份里的 `filled` 一致。数量不一致就返回空，当前记录保持 `unknown`。公开成交里已经能看到这两个 client id；要用那笔成交的数量，不要另编。
5. `#2` / `#3` 仍是 `unknown` 时，保留 03:37 的本地开仓标记和退出标记。没有 `t` 不早于该标记、且 `submitted` 的新 intent，这个标记不是新订单已提交的证据；但只要还有未知历史单，就不能删标记、不能当空仓放行。
6. 可选的只读核对：用已签名的 Lighter 私有历史，查 03:37:08 到 03:37:10 有没有新的 inactive order。未签名的 400 不算这项核对。Hyperliquid 该窗口订单和 fills 为 0，只能说明这一侧的官方查询没有看到新单。
7. 只有在第 4 步把 `#2` / `#3` 恢复到有官方数量支持的 `terminal`、未知订单列表为空，并且第 6 步没有发现新 client id 时，才可以另做一步：删掉 03:37 这个没有对应 intent 的本地开仓/退出标记。不删那 16 条 intent，不把模式改成 live，不改策略参数。
8. 若签名历史看到了新订单，停在这里。那是真实未知，按未知保护处理：不重发、不平未知腿、不把空仓当成已核实。

`audit_restore_intent` 没有 HTTP 路由，也不会在重启时自动跑。

## 和亏损上限的关系

两所合计亏损上限是另一项功能，默认 5U，只停止新开仓。它不能拿来掩盖这次历史单污染，也还没有部署。服务器仍是原 3x / 290U / 40bp，本任务没有重启。
